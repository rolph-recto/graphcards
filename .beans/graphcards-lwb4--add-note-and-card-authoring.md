Add an Anki-style note and card model while keeping deck imports clear.

## Plan

- [ ] Document the boundary between source-file entities and editable notes.
- [ ] Define strict Pydantic models for note types, fields, card templates, notes, and cards.
- [ ] Add stable note IDs and separate card IDs.
- [ ] Add one vertical slice for add, edit, delete, and duplicate checks.
- [ ] Add tags and multiple cards per note.
- [ ] Add migration and import tests without changing existing deck identity rules.
- [ ] Run the project validation commands.

## Acceptance checks

- A note can create more than one card.
- Editing one note updates all generated cards.
- Card identity is separate from note identity.
- Existing source-file decks still load and sync.

## Expanded implementation plan

### Scope and architecture boundary

- [ ] Keep `DeckDocument`, `Entity`, `Deck.load`, and the JSON, TOML, and YAML loaders as the source-file import boundary. Source entities stay immutable and read-only.
- [ ] Do not add editable note fields, tags, or card templates to `Entity` or to imported deck files. Do not write an authoring mutation back to a source deck file.
- [ ] Keep the current source-card identity `CardKey(deck_id, entity_id)` and the current `Repository.sync_deck` behavior. A note ID must not replace an entity ID, and a source import must not deactivate authored cards.
- [ ] Add a separate collection authoring path. The first vertical slice must support one basic note type, at least two card templates, note add, note edit, note delete, tags, card preview, and duplicate checks.
- [ ] Keep typed answers, rich media, image-occlusion editing, export, and full browser search out of this bean. Define stable authoring IDs so those later beans can use them.

### Dependencies and sequencing

- [ ] Use the current `graphcards-cpha` identity contract as an input. Resolve any future identity change before implementation, but do not reopen the source-card identity decision in this bean.
- [ ] Keep the authoring card ID independent of generator IDs. The current deck generators and the in-progress cloze work must not determine authoring card identity.
- [ ] Define route and response fields that the future `graphcards-03of` card browser can consume: note ID, card ID, note type ID, template ID, tags, and source kind.
- [ ] Keep typed answer and media concerns for `graphcards-csr1`. A note template may render escaped text fields only in this slice.

### Phase 1: domain and rendering contract

Affected modules: `src/graphcards/models.py`, `src/graphcards/references.py`, `src/graphcards/decks/base.py` or a new shared template module, and a new `src/graphcards/authoring.py`.

- [ ] Add strict Pydantic v2 models named `NoteField`, `CardTemplate`, `NoteType`, `Note`, and `AuthoredCard`. Use the existing frozen, extra-forbid model base where the model is immutable.
- [ ] Make note IDs and card IDs opaque UUID4 values generated by the repository. Do not derive either ID from field content, tags, generator IDs, or template text. Do not reuse an ID after a delete.
- [ ] Give `NoteType` a stable ID, display name, ordered fields, and ordered card templates. Require at least one field and one template. Require unique field names and unique template IDs within the note type.
- [ ] Give `CardTemplate` a stable template ID, display name, front template, and back template. Validate template length, unknown variables, and rendered output limits with the same sandbox and strict undefined behavior used by deck templates.
- [ ] Represent note fields as an exact mapping from declared field names to text values. Reject missing fields, unknown fields, non-string values, control characters, and values above the chosen per-field and total limits. Keep field order from the note type.
- [ ] Store tags as normalized, ordered, unique strings. Trim tags, reject blank tags and control characters, and enforce maximum tag length and tag count. Preserve tag order for display while using a canonical form for comparisons.
- [ ] Materialize one `AuthoredCard` for every active template on a note. Store `card_id`, `note_id`, `note_type_id`, and `template_id`; do not reuse the existing generated-exercise `Card` model for this record.
- [ ] Make note type field and template definitions immutable after the type has notes. Require a new note type for incompatible field or template changes so existing card IDs remain stable.
- [ ] Define duplicate matching as the normalized first declared field within one note type. Normalize with trim, Unicode NFC, and case folding. Ignore tags. Allow the same first field in different note types. Exclude the current note when checking an edit. Reject a blank duplicate field in the first slice.
- [ ] Extract the safe Jinja renderer from private deck code only if needed. Preserve existing deck template behavior and add an authoring context that exposes declared field names only.

### Phase 2: persistence and transactional authoring service

Affected modules: `src/graphcards/storage.py`, `src/graphcards/errors.py`, and the new `src/graphcards/authoring.py`.

- [ ] Add an authoring repository/service boundary. The service must expose validated operations for create note type, list note types, create note, read note, update note, delete note, list materialized cards, render a card, and check duplicates. Flask routes must not issue SQL directly.
- [ ] Add separate SQLite tables for `note_types`, `notes`, `note_tags`, and `note_cards`. Store validated field and template data as unique-key JSON documents. Use foreign keys, unique constraints, timestamps, an active or deleted marker, and an index for duplicate lookup.
- [ ] Give `note_cards` a global `card_id` primary key and a unique `(note_id, template_id)` constraint. Keep note deletion as a transactional soft delete or inactive transition so review history and old IDs are not silently reused.
- [ ] Make create, edit, and delete atomic. Create must insert the note and all template cards in one transaction. Edit must update the note and its tags without changing any existing card ID. Delete must deactivate every card for the note in the same transaction.
- [ ] Render authored card views from the current note fields and the referenced template. Do not copy stale front or back text into the identity record. An edit must therefore change every card view that uses the note while preserving each card ID.
- [ ] Enforce duplicate uniqueness in both the service and SQLite. Map a uniqueness race to a typed authoring conflict instead of returning a raw `sqlite3.IntegrityError`.
- [ ] Add an authoring error family below `GraphCardsError` for invalid input, duplicate notes, missing notes, and invalid template presentation. Translate Pydantic failures with the repository validation-message helper. Translate storage corruption to `StorageError`; do not expose SQL or parser internals.
- [ ] Keep the existing `cards`, `deck_cards`, and `reviews` source-card tables unchanged in the first slice. If authored cards later enter FSRS queues, add an explicit authored-card reference adapter instead of making `entity_id` optional or overloading the source-card key.

### Phase 3: web/API vertical slice

Affected modules: `src/graphcards/web/controller.py`, `src/graphcards/web/app.py`, new or updated templates under `src/graphcards/web/templates/`, and `src/graphcards/web/style.src.css` if the new forms need styles.

- [ ] Add a controller service for note and card operations. Scope every read and mutation to the selected collection or note type, and verify ownership in the repository instead of trusting hidden form fields.
- [ ] Add server-rendered routes for note list and add, edit, delete, duplicate check, and card preview. Use the existing URL-encoded form pattern unless a separate JSON contract is required by the browser bean.
- [ ] Add Pydantic request models with strict extra-field rejection for note type, note ID, field values, tags, and CSRF token. Return 400 for invalid forms, 404 for an unknown or deleted note, and 409 for a duplicate or stale mutation.
- [ ] Preserve the existing expected-host check, CSRF token check, no-store headers, and safe error pages on every state-changing authoring route. Do not add an authoring route to the study-only endpoint allowlist.
- [ ] Add a separate authoring body limit and field-count limit. Do not increase the current study form limit without a reason. Do not reflect raw invalid field values in an error page.
- [ ] Escape rendered note values and keep template execution in the sandbox. Reject template variables outside the declared field set and reject output that exceeds the existing rendering cap.
- [ ] Add links from the local deck hub only if the authoring collection is available. Do not make application startup mutate source deck files or create a note for every imported entity.
- [ ] Do not merge authored cards into the current `StudySession` queue in this first slice unless the implementation adds a separate `AuthoredCardRef` path. If queue integration is included, update `app.py`, `web/study.py`, and `web/status.py` through that reference and add identity tests; never use a blank or synthetic `entity_id`.

### Phase 4: migration and source import compatibility

Affected modules: `src/graphcards/storage.py`, `tests/test_integration.py`, the format-specific deck tests, and a new migration test module.

- [ ] Bump the state schema from version 7 to a new version for the authoring tables. Add an explicit transactional 7-to-new-version migration and create all tables at the new version for a fresh database.
- [ ] Keep the current no-silent-reset policy. Reject unsupported schema versions and failed migrations as `StorageError`. Leave the database usable at its old version when a migration transaction fails.
- [ ] Do not convert existing entities into notes automatically. Preserve existing source cards, deck memberships, review rows, deck directory identity, generator-change schedule behavior, and JSON/TOML/YAML import behavior.
- [ ] Test a migrated database that contains source cards, suspended memberships, and review history. Verify that those rows retain their current composite source identity after the new authoring tables are added.
- [ ] Test that authoring CRUD cannot alter source entities or source-card membership, and that a source `sync_deck` cannot delete or duplicate authored notes and cards.

### Security and failure controls

- [ ] Validate every external value before a database write. Use bound SQL parameters, foreign keys, uniqueness constraints, and one transaction per mutation.
- [ ] Use optimistic note version or updated-at checks for edit forms so an older form cannot overwrite a newer edit. Return a safe conflict response.
- [ ] Treat note IDs, card IDs, template IDs, and note type IDs as untrusted route input. Validate their format and verify their relationship before every read, preview, edit, or delete.
- [ ] Apply limits to field count, field size, tag count, tag size, template size, total request size, JSON depth, and rendered output size.
- [ ] Reject control characters and line separators in IDs, field names, tags, and template metadata. Normalize only the values that the duplicate rule specifies.
- [ ] Keep CSRF, host validation, content-type validation, and same-origin form actions on mutations. Do not add a state-changing GET route.
- [ ] Convert template parse or render failures to a safe authoring or presentation error. Convert storage corruption to the generic 500 response already used by the web application. Do not return Pydantic tracebacks, SQL text, or filesystem paths to the browser.

### Test strategy

- [ ] Add model tests for strict extras, missing and unknown fields, field and template uniqueness, blank values, control characters, tag normalization, UUID identity, template variable validation, and frozen model behavior.
- [ ] Add authoring service tests for create, read, update, delete, duplicate lookup, duplicate conflict, tag persistence, two or more cards per note, stable note and card IDs, and render changes after a note edit.
- [ ] Add transaction tests that force a bad template, a missing foreign key, a duplicate race, and a storage failure. Verify that no partial note, tag, or card rows remain.
- [ ] Add property tests for one-to-many cardinality, ID stability across edits, ID non-reuse after deletes, duplicate canonicalization, tag order and de-duplication, and mutation atomicity. Reuse the existing Hypothesis settings and strategy style.
- [ ] Add web tests for valid add, edit, delete, duplicate responses, card previews, missing IDs, stale versions, invalid CSRF, wrong hosts, wrong content types, oversized forms, malformed encodings, XSS escaping, and no state mutation after rejected requests.
- [ ] Add migration tests for fresh schema creation, 7-to-new-version upgrade, idempotent startup, rollback on migration failure, and unsupported or corrupt schemas.
- [ ] Extend JSON, TOML, and YAML import and integration tests to prove that source decks still validate, load, sync, and keep the current `(deck_id, entity_id)` identity after authoring data exists.
- [ ] Run `uv run pytest -W error`, `uv run ruff check .`, `uv run ruff format --check .`, and `uv build`. Rebuild the committed Tailwind stylesheet only if the implementation changes the source stylesheet.

## Definition of done

- [ ] A valid note type can define strict fields and at least two card templates.
- [ ] A note receives one stable note ID and creates more than one card with distinct stable card IDs.
- [ ] Editing a note changes the rendered content of every generated card, keeps all card IDs stable, and keeps source-file cards untouched.
- [ ] Tags persist with normalized values and appear in the note and card API responses.
- [ ] Duplicate checks are deterministic, scoped to a note type, exclude the note being edited, and remain safe under concurrent creates.
- [ ] Delete removes the note from authoring views and deactivates all of its cards atomically without reusing IDs.
- [ ] The web vertical slice supports add, edit, delete, duplicate check, and preview with safe 4xx responses and CSRF protection.
- [ ] A version 7 state database migrates without losing source schedules, memberships, or review history, and a failed migration does not partially apply.
- [ ] Existing JSON, TOML, and YAML source decks still load and sync with their current deck directory and entity identities.
- [ ] The required validation commands pass, the bean implementation checklist remains unchecked until implementation, and no generated database or workspace artifact is included.
